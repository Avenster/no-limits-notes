## Fix: Code-block syntax highlighting

### Root cause (confirmed)
In `frontend/app/pages/NoteEditor.tsx:119-126`, the custom highlight extension is registered under a property name **BlockNote does not recognize**:

```ts
createExtension({
  key: "codeHighlight",
  prosemirrorPlugin: () => createHighlightPlugin({...}),  // ❌ not a real property
})
```

BlockNote's `Extension` type requires `prosemirrorPlugins?: Plugin[]` (plural, an array). Because `prosemirrorPlugin` is silently ignored, your highlight plugin is constructed and discarded — it never attaches to the editor. Meanwhile BlockNote's *built-in* code-block highlighter is also active but returns `[]` because no Shiki `createHighlighter` was provided. So neither plugin produces decorations → no syntax colors, even though the language dropdown correctly writes `props.language` onto the block (your exact symptom).

### Chosen approach: lowlight adapter
Use `prosemirror-highlight`'s official `lowlight` adapter instead of the fragile hand-rolled DOM-walking parser. This replaces shared-mutable offset math with offset computation straight off the HAST tree (SSR-safe, no `document.createElement`), and keeps your existing highlight.js language registrations and CSS theme.

### Changes (all in `frontend/app/pages/NoteEditor.tsx`)

1. **Add dependency** — `npm install lowlight` in `frontend/`. (`prosemirror-highlight` is already available transitively; `lowlight` v3 returns the HAST tree its adapter expects.)

2. **Swap highlight.js import for lowlight** (lines 10-24):
   - Import `lowlight` from `lowlight` instead of `hljs` from `highlight.js/lib/core`.
   - Keep the same per-language imports (`highlight.js/lib/languages/...`).
   - Register with `lowlight.registerLanguage("javascript", javascript)` etc. (same name + alias list as today). lowlight exposes `registerLanguage` mirroring highlight.js.
   - Keep `import "highlight.js/styles/github-dark.min.css";` — the class names lowlight emits (`hljs-keyword`, `hljs-string`, …) are identical to highlight.js, so your existing theme + `.hljs-*` overrides in `app.css` keep working unchanged.

3. **Replace the hand-rolled `hljsParser`** (lines 67-108) with the official adapter:
   ```ts
   import { createParser } from "prosemirror-highlight/lowlight";
   const hljsParser = createParser(lowlight);
   ```
   The adapter calls `lowlight.highlight(language, content)` → walks the HAST tree → emits `Decoration.inline` with correct offsets (`pos + 1 + …` handled internally). Unknown/text languages still produce no decorations automatically.

4. **Fix the extension property** (lines 117-128):
   ```ts
   const codeHighlightExtension = useMemo(
     () => createExtension({
       key: "codeHighlight",
       prosemirrorPlugins: [ createHighlightPlugin({ parser: hljsParser, nodeTypes: ["codeBlock"] }) ],
     }),
     []
   );
   ```
   - `prosemirrorPlugin` → `prosemirrorPlugins` (plural).
   - Value is the plugin instance directly (not a `() =>` function). `createHighlightPlugin(...)` returns a `Plugin`, passed in an array.

5. **Leave untouched**: the `useCreateBlockNote({ extensions: [codeHighlightExtension] })` wiring, the hover/copy overlay, the language dropdown (it already calls `editor.updateBlock(id, { props: { language } })` correctly), and `app.css` `.hljs-*` rules.

### Why this is safe
- One file edited; the editor API and language dropdown already work — only the decoration pipeline was broken.
- No schema rewrite, no Shiki bundle, no change to how blocks are stored or saved.
- Class-name compatibility means zero CSS changes.
- `prosemirror-highlight` stays a transitive dep (importing its `lowlight` subpath is its documented public API).

- Expect colored tokens (keywords, strings, comments, numbers) appearing immediately.
